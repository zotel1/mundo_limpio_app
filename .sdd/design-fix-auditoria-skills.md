### Architecture Decisions

**Why domain entities instead of abstract return types**: Domain entities are the standard pattern
in Clean Architecture. The repository contract defines WHAT data flows (entities), the implementation
defines HOW (mapping from DTOs). This is consistent with the existing pattern used for `Sale`,
`Receipt`, `Purchase` entities.

**Why NOT move the DTOs to domain**: Moving DTOs (with `@JsonSerializable` annotations) to domain
would introduce json_annotation as a domain dependency, violating the "domain has no external
dependencies" rule. Domain entities stay pure Dart.

**Why sealed ApiException + switch**: The current if-else chain is fragile — adding a new exception
subtype is silently handled by the generic fallthrough. A sealed class + switch expression makes
the compiler enforce exhaustiveness: adding a new subtype forces updating all switch sites.

None — purely internal refactoring. No external dependency changes.

with no navigation. Redirecting to home is a graceful degradation. If state.extra is null, it means
the route was reached via an unexpected path (browser history, deep link) — the safest action is
to return to a known state.

## B4 — HTTP Safety & Linting

### Technical Approach

**W3 — CancelToken in all API calls** (CONFIRMED):

Zero `CancelToken` usage found across ALL 7 API files (grep returned "No files found"). Every
`_dio.get/post/put/patch/delete` call needs a `cancelToken` parameter.

**Fix strategy**:
1. Each API class (`AuthApi`, `SalesApi`, `ProductsApi`, `InventoryApi`, `UsersApi`, `ReceiptsApi`)
   receives an optional `CancelToken?` parameter in its constructor
2. Each HTTP method accepts an optional `CancelToken? cancelToken` parameter
3. Callers (providers/repositories) pass `CancelToken` when they want cancellation control
4. Providers create a `CancelToken` in their init/dispose lifecycle, cancel on dispose

**Pattern**:
```dart
class SalesApi {
  final Dio _dio;
  const SalesApi({required Dio dio}) : _dio = dio;

  Future<List<ProductResponse>> getProducts({CancelToken? cancelToken}) async {
    final response = await _dio.get('/api/v1/products', cancelToken: cancelToken);
    ...
  }
}
```

Memory leak scenario: without CancelToken, if a user navigates away while a request is in-flight,
the response callback holds a reference to the widget tree. The request continues executing on
the event loop, preventing GC. CancelToken lets Dio abort the request on dispose.

**W9 — Linter rules** (CONFIRMED):

`analysis_options.yaml` has commented-out rules (lines 38-39). Three rules to add:

1. `avoid_print: true` — prevents debug `print()` in production code
2. `use_super_parameters: true` — enforces `super.key` pattern instead of manual forwarding
3. `require_trailing_commas: true` — enforces trailing commas for cleaner diffs and auto-formatting

Current file already uses `super.key` in most widgets (verified in multiple screens), so
`use_super_parameters` should produce zero or very few warnings.

in 15+ screens using `const XxxScreen({super.key})`). Making it a lint rule prevents regression.

## B6 — Test Hygiene & Smoke

### Technical Approach

**W8 — create_sale_screen_test hit test warnings** (CONFIRMED):

Lines 177, 214, 239, 309 in the test file tap on text inside a dropdown overlay. The pattern is:
```dart
await tester.tap(find.text('Seleccioná un producto'));  // opens dropdown
await tester.pumpAndSettle();
await tester.tap(find.text('Producto A').last);          // taps item in overlay
```

This triggers "A RenderFlex overflowed..." or hit test warnings because the dropdown overlay
renders outside the normal widget tree. The `.last` finder is picking up the item IN the overlay.

**Fix strategy**: Use `tester.tap(find.text('Producto A').last)` but ensure the dropdown overlay
is fully rendered before tapping. Add `await tester.pumpAndSettle()` with a longer settle duration,
or use `await tester.tap(find.byKey(...))` with explicit keys on dropdown items.

Alternative: wrap dropdown tap in `await tester.ensureVisible()` before tapping the item.

### Architecture Decisions
**Why not restructure the test to avoid dropdown overlay entirely**: The test validates real user
behavior (open dropdown, select item). Restructuring to a non-dropdown flow would test a different
scenario. The fix should address the test mechanics, not change the scenario.
